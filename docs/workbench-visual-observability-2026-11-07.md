# Project visual workbench: data, behavior and acceptance

**Status:** active Connectome implementation plan and evidence for [PR #43](https://github.com/rrflow/connectome-development/pull/43); H-06 and the RRFlow roadmap own acceptance.

The workbench gives the operator one place to submit a prompt, inspect returned execution events, see the project's records and relationships, and inspect storage behavior. The engine owns facts, identity, authorization, event order and durability. Connectome owns presentation, local navigation and bounded rendering. A view must say what was actually read and what it does not know.

## Implemented in this candidate

| Surface | Input and authority | Interaction and limits | Evidence boundary |
| --- | --- | --- | --- |
| Prompt and flight | Authenticated `launchObserveFlight`, cursor-paged flight listing and selected flight readback | Explicit prompt submission, session-scoped selection, refresh and paging. | Project graph | Existing authenticated `database()` diagnostic view, its returned nodes/edges, read time and graph cursor | Select a 20/40/80-record preview, click a record or use the keyboard list to open it in the existing graph lens. Missing counters say not reported. | The observation is process-local and timestamped; it is independent of the graph's read cursor. Sync policy and recovery govern durability. ## Complete visual direction and dependencies

1. **Real project intake and lifecycle:** show selected source, inventory progress, exclusion/denial and durable checkpoint, then parse/index availability and last successful source stamp. These require the engine's authorized source inventory and parser publication; installation or a drawn graph is not proof of indexing. A real-project test must edit/delete a file, replan, restart and show the changed source-derived result.
2. **Prompt execution and retrieval:** visualize engine-issued plan/capability decisions, skipped and unavailable avenues, source identities, budgets, truncation and event lineage. Dense/lexical/vector/graph lanes appear only when an engine result identifies them. Prompt-local and durable effects must be distinguishable and their receipts inspectable. Existing observe-only flight events are the first supported event input, not a complete reasoning trace.
3. **LFG, SWAG and configurable providers:** add typed adapters to the engine's public capabilities when available. Show the actual classifier labels, complexity, confidence and configuration/provenance returned for a request; show the router's selected route and evidence. A named component is not shown as active merely because it is configured. Custom endpoints, disabled/unavailable/error states and effective configuration origin need equal treatment.
4. **MCP and tool activity:** show only authorized, engine-correlated requests and returned receipts. The visual event order is not an MCP topology; an actual mesh/hop view needs endpoint, operation, parent/span identity, timestamps and redaction from a public engine contract.
5. **Storage and performance:** add sourced cache/flush/compaction series and comparisons only when the engine exposes timestamps, units and reset semantics. Cold Parquet archival remains unavailable until its engine lifecycle exists. Benchmarks must identify corpus, hardware, configuration, exact binaries, quality criteria, warmup, repetitions and failures; no inferred performance claim belongs on the dashboard.
6. **Human feedback and learning:** make an explicit review action attach a label or preference to its provenance and authorization. Preserve corrections, deletion, consent and project isolation. No unattended training, prompt interception or model-improvement claim follows from a local note.
7. **Large projects and accessibility:** server-supplied pagination, cancellation, bounded graph requests and virtualized lists precede large-data claims. Maintain a textual/keyboard route to the same records and events, responsive layout, contrast, screen-reader names, and reduced-motion behavior. Do not turn client-computed clusters or positions into durable graph facts.
8. **Structured adaptive UI:** a future engine-supplied, versioned presentation envelope may select only supported, accessible Connectome components with bounded data and typed actions. Each action needs its public capability, target, authorization and receipt; unsupported versions or components must render an explicit fallback. No arbitrary script execution or unvalidated model-produced UI becomes an execution authority. A renderer conformance corpus must cover unknown fields, size/depth budgets, accessibility and replay before this is offered as a standard.

Every future panel should expose the source instance, observation time or cursor, configured limits, partial/truncated state and a route to the underlying evidence when the relevant contract provides them. Filters and layouts may change presentation; they must not silently change the engine's stored relationships, claim a total from a bounded page, or mix records from different projects. Configuration controls must show effective values and origins and send changes through the engine's authorized preview/apply operations. These are acceptance requirements for later engine-backed work, not claims that the current workbench implements those operations.

## Verification and stop conditions

Use a clean optional Connectome checkout and exact engine/SDK pin. First exercise a real installed engine with a synthetic document/edge fixture, graph cursor, storage observation and observe-flight readback; show the fixture and limitations. Then use a copied real project and compare source identity, indexing status and retrieval with independent expectations. Repeat after edit, interruption and restart. Check profile/session switches, refused operations, no data, partial responses, accessibility and both desktop themes/sizes. Protect user data and credentials; native visual testing uses a separate scratch profile and stops only processes it starts.

This candidate can establish a usable visual surface for data the current engine returns. It cannot close H-06, D-04, C-07 or the alpha: current real-source Parse remains unavailable, full retrieval and LFG/SWAG execution are not shown, and cross-platform release/soak evidence remains outstanding.

An isolated-port Playwright run initially failed three existing session-switch tests because their deferred graph/storage fixtures returned incomplete objects after the new views began reading them. Running preview after the build completed passed all 11 tests, including visual/keyboard/event, empty/error and all four existing stale-capture scenarios. These are controlled browser tests, not proof of native engine state. A local exact-pin engine binary was built offline; the single-link copy has SHA-256 `a9668c069f31016991471b5b65e8d8d42162d15a4e143d76067f329691e0a8ac`. Final candidate CI, merge-group CI and real-source indexing remain outstanding.

An earlier native Windows run against that engine used a synthetic fixture of 19 records and 14 edges. It captured 60 screens and returned no harness failures; the observe flight used the engine's observe provider. This establishes rendering of that fixture, not real-source indexing. The native runner used an isolated local profile override that is not product code.

A separate copied real project contained 2,315 tracked files at source revision `bf6dec69f1ca8c37d97dbd447af128ce33c390be`. Connect and Inventory completed; Parse returned `phase-unavailable`. The graph did not render: the full diagnostic response measured 10,978,959 bytes and even the response without comparison history measured 5,573,982 bytes, exceeding the 4 MiB client response limit. The existing physical-storage operation returned 2,132 bytes in the same probe. This candidate uses that operation for the workbench storage panel, but it does not fix the full storage lens or the graph response. An engine-owned bounded graph read with explicit completeness, pagination and source identity is required; raising the limit or silently truncating would not resolve that contract. Measurements apply to this copied project and engine revision, not a general performance claim.

On Windows the native process test `rrd::client::process::the_lenses_read_a_live_estate` passed against the pinned engine, including the new physical-storage read. A scratch-profile desktop run of the copied project displayed the graph-size error and, separately, live rrflowKV WAL, memtable, segment and page-cache observations. The local runner's profile override is not part of the product. This confirms the workbench remains useful during that graph failure; it does not prove complete graph retrieval or indexing. A simultaneous second desktop capture failed because the application permits only one instance, so captures must run sequentially.

## Design references

[WCAG 2.2](https://www.w3.org/TR/WCAG22/) requires keyboard-operable functionality and that color not be the only way information is conveyed. The record list and textual event details support those goals; they do not by themselves establish WCAG conformance. [OpenTelemetry's trace model](https://opentelemetry.io/docs/specs/otel/overview/) defines parent/child relationships using span context, so this workbench does not infer a network topology from a list of ordered events. Its [metrics data model](https://opentelemetry.io/docs/specs/otel/metrics/data-model/) distinguishes cumulative and delta observations and their time windows; future rate charts need source timing and reset semantics rather than differences guessed across restarts.
